# 2026-06-06 — 飞连API列表 / 飞连任务列表 UI 改版设计

## 1. 背景

当前界面已经完成若干轮拆分与重构，但仍存在三个明显问题：

1. `飞连API列表` 虽然已经拆出独立页面，但页面内部仍偏“三块拼接”，右侧缺少更稳定的上下信息分区。
2. `飞连API任务` 与 `飞连周期任务` 仍然是两个一级页面，用户在“单次任务”和“定时任务”之间来回跳转，心智割裂。
3. `飞连周期任务` 的调度配置仍带有偏技术化字段：
   - `cron`
   - `interval`
   - `timezone`
   对业务用户不够友好。

此外，当前还暴露了一个实际 bug：

> `飞连API任务` 左侧任务列表只能稳定展示最近一条任务草稿，而不是完整任务清单。

本轮改版目标，是进一步把页面信息架构调整成“模板中心 + 任务中心”两大工作流。

---

## 2. 目标

本次设计目标如下：

1. 将 `飞连API列表` 调整为左右结构：
   - 左侧：`飞连API列表`
   - 右侧：上下结构
     - 右上：`模板详情`
     - 右下：`执行输出`
2. 将 `飞连API任务` 与 `飞连周期任务` 合并为一个一级页面：
   - `飞连任务列表`
3. 在 `飞连任务列表` 内设置两个二级页面 Tabs：
   - `单次任务清单`
   - `定时任务清单`
4. 保持两类任务原有核心能力不变，只重构信息组织方式
5. 修复 `单次任务清单` 仅展示最近一条任务的 bug
6. 将 `定时任务清单` 的调度编辑方式改成业务友好的时间配置方式

---

## 3. 非目标

本轮不做以下事情：

- 不重写后端调度引擎
- 不改动任务执行链路和 webhook runtime 语义
- 不重做模板编辑器
- 不引入新的路由系统
- 不增加新的任务类型

本轮只聚焦：

- 页面重组
- 表单交互简化
- 已有功能的更合理承载

---

## 4. 方案对比

## 4.1 方案 A：模板中心 + 任务中心（推荐）

### 方案描述

保留 `飞连API列表` 作为独立一级页面；将 `飞连API任务` 与 `飞连周期任务` 合并为新的一级页面 `飞连任务列表`，在页内通过顶部 Tabs 切换：

- `单次任务清单`
- `定时任务清单`

### 优点

- 一级导航更干净
- 用户能明确感知“模板”和“任务”是两个不同中心
- 单次任务与定时任务属于同一任务域，合并后更符合心智
- 后续如增加任务统计、最近运行记录，也更容易统一放入任务中心

### 缺点

- 需要重组现有导航和部分按钮返回路径

### 结论

**采用本方案。**

---

## 4.2 方案 B：保持两个一级任务页面，只做局部布局优化

### 方案描述

保留：

- `飞连API任务`
- `飞连周期任务`

仅分别优化各自布局。

### 优点

- 实现改动较小

### 缺点

- 无法解决“任务中心割裂”的根本问题
- 用户仍要在两个一级导航之间跳转

### 结论

不采用。

---

## 4.3 方案 C：把模板、单次任务、定时任务全部放回一个超级页面

### 方案描述

将三者集中到同一页，用多 Tabs 或大分区承载。

### 优点

- 看起来页面数量最少

### 缺点

- 与此前已完成的“模板与任务拆分”方向相冲突
- 页面职责重新混杂，回到旧问题

### 结论

不采用。

---

## 5. 最终信息架构

一级页面结构调整为：

1. Dashboard
2. 连接配置
3. `飞连API列表`
4. `飞连任务列表`
5. 运营agent
6. Logs

其中：

- `飞连API列表`：聚焦模板管理与模板测试
- `飞连任务列表`：聚焦单次任务草稿与定时任务

`飞连周期任务` 将不再作为独立一级导航出现，而被吸收到 `飞连任务列表` 中的二级 Tabs。

## 6. 飞连API列表页面设计

## 6.1 布局结构

页面调整为标准左右结构：

- 左侧：`飞连API列表`
- 右侧：上下分区
  - 上：`模板详情`
  - 下：`执行输出`

建议比例：

- 左：约 50%~55%
- 右：约 45%~50%

右侧再按上下 1:1 或 5:4 分配。

---

## 6.2 左侧区域：飞连API列表

保留当前能力：

- 刷新
- 新增模板
- 搜索/筛选
- 模板表格
- 测试 / 编辑 / 删除 / 用此模板创建任务

但左侧区域只承载“列表”本身，不再与详情/输出并列拼块。

---

## 6.3 右上区域：模板详情

显示当前选中模板的详情，主要用于只读查看。

建议展示内容：

- 模板 ID
- 名称
- category
- method
- path
- schema / 原始 JSON

表现形态可以保留当前 `pre + pretty JSON`，不要求本轮改成复杂卡片。

---

## 6.4 右下区域：执行输出

固定承接模板测试输出。

建议保留：

- `Copy`
- `Clear`

输出规则：

- 点击模板“测试”后，无论成功/失败，结果都刷新到右下输出区
- 不与任务执行输出混用

这样模板页右侧形成非常清晰的上下逻辑：

- 上面看“模板本身”
- 下面看“模板执行结果”

---

## 7.3 单次任务清单需要修复的 bug

当前左侧任务列表仅能稳定展示最近一条任务草稿。

本轮必须修复为：

## 8. 定时任务配置改造

## 8.1 `cron` 改成“任务定时窗口”

当前：

- 使用 `cron` 文本或偏技术化表达

改版后：

- 改成“任务定时窗口”
- 使用 **24h 制时分选择器**

也就是用户不再直接输入 cron，而是通过：

- 小时选择
- 分钟选择

来确定每天执行时间点。

第一版建议语义：

- 当用户选择具体时分时，系统在保存时自动转换成内部 cron 表达式

例如：

- 09:30 → 内部转换为对应的 cron

注意：

- UI 展示不再暴露 `cron` 文本输入框
- 底层存储仍可继续保存 cron 字符串，不要求本轮重写调度存储模型

---

## 8.2 `interval` 改成固定选项

当前：

- `interval` 是自由输入或技术化字段

改版后：

- 改成固定选项下拉：
  - `5min`
  - `30min`
  - `1h`
  - `6h`
  - `24h`
  - `7day`
  - `1month`
  - `1year`

这样业务用户不需要理解秒、分钟换算，也不需要自己输入表达式。

系统内部再把这些选项映射到已有调度字段。

---

## 8.3 删除 `timezone`

当前：

- 调度配置显式暴露 `timezone`

改版后：

- 删除该输入项
- 默认绑定当前服务器时区

页面上可以补一条只读提示：

- `默认使用当前服务器时区`

但不需要让用户再选择。

---

## 8.4 调度方式建议

定时任务建议在 UI 中分成两类模式：

1. `每日定时`
   - 使用 24h 时分选择器
2. `固定间隔`
   - 使用固定 interval 选项

这样比直接暴露：

- `cron`
- `interval`

更易理解。

如果当前代码里已有 `schedule_type`，则建议继续复用，只是在 UI 上重命名和重包装。

## 12. 风险与注意事项

## 12.1 `cron` 只是被 UI 隐藏，不是被删除

本轮只是：

- 不让用户直接输入 cron
- 改由更友好的时间选择器生成 cron

因此实现阶段要特别注意：

- UI 层与存储层字段映射必须保持一致

---

## 12.2 `1month / 1year` 的间隔语义需明确

这两个选项本质上不是纯秒级固定间隔。

实现阶段应明确：

- 是用 cron 表示“每月同一日同一时分”
- 还是用内部 interval 近似值

推荐做法：

- `1month` / `1year` 也走 cron 化表达

这样语义更稳定。

---

## 12.3 任务列表 bug 修复优先级高

虽然本轮是 UI 改版，但“单次任务只显示最近一条”是用户已明确感知到的功能缺陷。

因此它不应被视为顺手优化，而应纳入本轮的正式验收项。

---

## 13. 推荐实施顺序

建议实现时按以下顺序推进：

1. 调整导航与页面命名
2. 重构 `飞连API列表` 页面为左右 + 右侧上下结构
3. 创建 `飞连任务列表` 容器与顶部 Tabs
4. 把现有 `飞连API任务` 内容迁入 `单次任务清单`
5. 修复单次任务列表只显示最近一条的问题
6. 把现有 `飞连周期任务` 内容迁入 `定时任务清单`
7. 将 cron / interval / timezone 改造成新的业务化时间配置表单

这样每一步都可独立验证，风险最低。
