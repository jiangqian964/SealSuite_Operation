# 2026-06-05 — 模板列表与飞连API任务拆分（含右侧独立执行输出窗口）设计说明

## 1. 背景与问题

当前“飞连API任务”页面同时承载了：

- 模板列表（管理/维护视角）
- 模板详情（JSON）
- 模板测试入口（测试/调试视角）
- 飞连API任务定义（草稿/执行视角）
- 执行输出（结果/排障视角）

在同一页内混合多种工作流后，出现了用户可用性问题：

- 点击“测试完成”后，用户很难稳定定位到返回结果（输出区不明显/容易被滚动带走）
- 模板管理操作与任务定义操作相互干扰，心智负担较重
- 模板测试的输出与任务执行输出共用同一输出区，语义混乱

本设计将“模板管理/模板测试”与“任务定义/任务执行”拆成两个页面，并在“模板列表”页提供固定可见的独立输出窗口。

---

## 2. 目标（Goals）

1. **信息架构拆分**：将“模板列表”与“飞连API任务定义”拆分为两个一级页面入口。
2. **模板测试结果可见**：在“模板列表”页面增加右侧固定的“执行输出窗口”，测试后结果必然可见。
3. **职责清晰**：
   - 模板列表页：筛选、查看、编辑、测试模板 + 看测试输出
   - 任务定义页：编辑草稿、Preview/Execute、保存草稿 + 看执行输出
4. **交互一致**：统一成功/失败输出展示策略（toast 仅做提示，结果与错误必须写入输出窗口）。

---

## 3. 非目标（Non-goals）

- 不在本次设计中重做接口协议与存储结构（仍使用现有 `/api/v1/api/templates`、`/api/v1/api/templates/{id}/test`、`/api/v1/api/execute` 等接口）
- 不引入复杂的多标签路由（不做 URL hash/多页路由；仍是单页多 view 切换）
- 不对模板编辑器（Template Editor）的表单/JSON 双模式做功能增强（仅调整入口与布局）

---

## 4. 用户与使用场景

### 4.1 管理员/维护者（模板维护）

典型路径：

1. 打开“模板列表”
2. 搜索/筛选模板
3. 点击“测试”
4. 在右侧输出窗口查看最新响应/错误
5. 必要时进入编辑器修改模板并保存

### 4.2 任务编排者（草稿/执行）

典型路径：

1. 打开“飞连API任务”
2. 填写/加载草稿
3. Preview/Execute
4. 在任务页输出区查看结果/错误
5. 保存草稿

## 6. 页面设计（核心）

## 6.1 模板列表页面（新增页面）

### 布局（推荐：三栏结构）

**左侧（主列）：模板列表**

- 搜索/筛选（id/name/category）
- 表格：id / category / method / path / actions（测试/编辑/删除）

**中间（详情列）：模板详情**

- 只读 JSON（或简要字段卡）
- 作为“当前选中模板的说明区”

**右侧（固定）：执行输出窗口（新增）**

目的：模板测试与模板执行结果的稳定承载区，避免“toast 提示完成但找不到输出”。

输出窗口要求：

- 固定可见（不随左侧列表滚动丢失）
- 可折叠/展开
- 支持 Clear / Copy
- 展示结构化信息：
  - 模板 id、时间、HTTP 状态、latency
  - 业务 code/message（如果有）
  - 原始 body（pretty JSON）
- 结果写入规则：
  - 点击“测试”后，无论成功/失败，输出窗口都被刷新
  - 若输出窗口折叠，则自动展开并高亮一次

### 交互细节

- “测试”：调用 `/api/v1/api/templates/{id}/test`
- 输出写入：写入模板页的“输出窗口”，不复用任务页 `api-out`
- “编辑”：进入模板编辑器（已有 `template-editor` view）
- “新增模板”：进入模板编辑器（create 模式）

---

## 6.2 飞连API任务页面（改造后的任务定义页）

任务页职责收敛为“任务草稿定义 + 任务执行”：

- 草稿字段（id/name/mode）
- 请求配置（template_id / method / path / query / path_params / body）
- transform/llm/output（保持）
- Preview/Execute/保存草稿
- 执行输出（保持在页面内）

### 与模板列表的联动（建议）

在模板列表页提供一个按钮：

- “用此模板创建任务”

行为：

- 跳转到“飞连API任务”页面
- 自动将 `template_id` 预填为所选模板 id
- 可选：自动填 `method/path`（只读或同步）

> 注：此联动属于体验增强，可在实现期根据成本决定是否本轮上线。

## 7. 技术实现边界（用于实现阶段对齐）

> 本章节描述实现形态，仍不直接落代码。

### 7.1 前端 view 切换

现有逻辑通过 `setView('xxx')` 切换不同 `section.view`。

新增 view：

- `view-templates`：模板列表页面（新增）

保留/复用：

- `view-api`：飞连API任务（任务定义）
- `view-template-editor`：模板编辑器

### 7.2 输出窗口隔离

模板列表页新增输出容器（例如 `#tpl-out`），并将模板测试输出写入此容器。

任务页仍使用 `#api-out`。

### 7.3 后端 API

不新增新接口，复用现有：

- GET `/api/v1/api/templates`
- POST `/api/v1/api/templates/{id}/test`
- POST `/api/v1/api/templates`（新增模板）
- PUT `/api/v1/api/templates/{id}`（更新模板）
- DELETE `/api/v1/api/templates/{id}`（删除模板）

## 8. 可观测性与错误展示

### 8.1 展示原则

- toast：仅提示“成功/失败”，不承载细节
- 输出窗口：必须展示完整错误详情与 runtime_connection（若后端返回）

### 8.2 输出内容结构

建议在输出窗口内展示一个结构化头部：

- title：模板测试成功/失败
- template_id
- ts（本地时间）
- http_status / latency_ms（如果有）

以及一个可复制的正文：

- pretty JSON（raw body 或结构化 body）

---

## 9. 验收标准（Acceptance Criteria）

1. 导航新增“模板列表”入口，点击可进入新页面。
2. 模板列表页点击“测试”后：
   - 输出窗口必然可见并更新内容
   - 不会出现“提示测试完成但页面看不到返回结果”
3. 任务定义页不再承载模板列表（或模板列表入口明显弱化），页面心智负担降低。
4. 模板测试输出与任务执行输出不再混用同一个输出容器。
5. 所有按钮响应稳定（不再出现无反应/静默失败），失败时输出区能看到错误详情。

---

- 手工回归：
