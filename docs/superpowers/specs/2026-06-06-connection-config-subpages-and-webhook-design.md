# 2026-06-06 — 连接配置三子页与 Webhook 配置中心设计说明

## 1. 背景

当前系统中的 `连接配置` 正在从简单配置页升级为统一的 API 配置中心。  
在上一轮设计中，页面已经开始向“左侧列表 + 右侧详情工作台”演进，但随着需求继续扩展，现有结构又出现了新的问题：

1. `飞连_API`、`LLM_API`、`webhook配置` 三类对象已经不适合继续混在同一工作区里平铺展示
2. `LLM_API` 的管理模式发生变化：
   - 不再固定为 `Planner 模型 + Formatter 模型` 成对管理
   - 而是变成“单条 LLM API 配置 + 标签”
3. 系统新增了 `webhook配置` 的需求，用于让：
   - `飞连API任务`
   - `飞连周期任务`
   - `运营agent`
   的产出物支持推送到第三方系统

因此，本次设计的目标不再是“继续强化一个连接页”，而是把 `连接配置` 正式升级为：

> **包含三个独立子页面的配置中心**

---

## 2. 本次设计目标

本次设计目标如下：

1. 在 `连接配置` 下增加三个独立子页面：
   - `飞连API配置`
   - `LLM_API配置`
   - `webhook配置`
2. 每个子页面采用统一布局：
   - 左侧：配置列表
   - 右侧：配置详情
3. `LLM_API配置` 不再区分固定的 `Planner 模型 / Formatter 模型` 双栏结构
4. `LLM_API配置` 改为：
   - 一条配置 = 一条 LLM API 记录
   - 使用标签区分用途
   - 内置标签：
     - `Planner 模型`
     - `Formatter 模型`
   - 支持用户自定义其他标签描述
5. 新增 `webhook配置`：
   - 用作全局可复用的推送端点配置中心
   - 供业务对象按配置 ID 引用
6. webhook 需要提供：
   - 测试推送按钮
   - 模拟 payload 输入区

---

## 3. 非目标

本轮不做以下事情：

- 不直接实现第三方 webhook 的复杂签名协议适配（如企业微信、飞书、Slack 的专有签名方案）
- 不引入基于 URL 的多页路由
- 不改变飞连 token 获取逻辑
- 不在本轮里完成所有业务对象的 webhook 推送执行逻辑
  - 本轮先完成“配置中心设计 + 引用关系设计”

---

## 4. 信息架构

## 4.1 父级入口

`连接配置` 仍然是一级入口，但进入后不再只看到一个统一大页面，而是切换为一个**父级配置中心**。

该配置中心下包含三个独立子页面：

1. `飞连API配置`
2. `LLM_API配置`
3. `webhook配置`

可以通过页面内二级导航（Tab / Segment / 子导航按钮）切换。

---

## 5. 统一页面布局

这三个子页面统一采用相同结构：

- 左侧：`配置列表`
- 右侧：`配置详情`

这样用户形成一致心智：

- 左边 = 找配置 / 切换配置 / 管理配置
- 右边 = 看详情 / 编辑 / 新建 / 测试 / 输出反馈

## 5.1 左侧通用职责

左侧负责：

- 展示历史配置
- 搜索 / 筛选
- 标识 `ACTIVE`
- 删除
- 快速进入查看 / 编辑

## 5.2 右侧通用职责

右侧负责：

- 展示当前选中配置详情
- 支持查看 / 编辑 / 新建三态
- 提供测试能力
- 展示配置输出 / 测试输出

---

## 6. 子页面一：飞连API配置

## 6.1 左侧列表

左侧展示最近录入的飞连 API 连接配置。

每条记录建议展示：

- 名称
- 地址：`scheme://host:port`
- `AccessKey ID` 脱敏摘要
- `ACTIVE` 标签

操作：

- `查看`
- `设为 ACTIVE`
- `删除`

删除规则：

- 非 ACTIVE 项允许删除
- ACTIVE 项默认不允许直接删除

## 6.2 右侧详情

右侧展示单条飞连 API 配置详情，字段包括：

- 名称
- scheme
- host
- port
- AccessKey ID
- AccessKey Secret

状态：

- 查看态
- 编辑态
- 新建态

操作：

- `测试连接`
- `保存并热更新`
- `设为 ACTIVE`
- `删除`

输出区保留：

- token 获取结果
- probe 结果
- `token_request_preview`
- 保存反馈

---

## 7. 子页面二：LLM_API配置

## 7.1 核心变化

这部分是本次设计的关键变化点：

> `LLM_API配置` 不再按固定的 `Planner + Formatter` 双模型角色配置页面组织。

而改为：

> **一条配置 = 一条 LLM API 配置**

通过标签来表达它的用途。

---

## 7.2 标签设计

每条 LLM_API 配置支持一个或多个标签。

系统内置标签：

- `Planner 模型`
- `Formatter 模型`

并支持用户输入自定义标签，例如：

- `总结模型`
- `运营分析模型`
- `低成本模型`
- `长文本推理模型`

推荐交互：

- 使用标签输入框或可添加的 tag 组件
- 内置标签可快速点选
- 自定义标签可直接输入并添加

---

## 7.3 左侧列表

每条记录建议展示：

- 名称
- provider
- model
- base_url
- 标签摘要
- `ACTIVE`

操作：

- `查看`
- `设为 ACTIVE`
- `删除`

对 `ACTIVE` 的建议定义：

- 当前系统默认启用的 LLM_API 配置

这里的 `ACTIVE` 是“默认主配置”的语义，不再强绑定到固定角色。

---

## 7.4 右侧详情

右侧展示单条 LLM API 配置详情，字段包括：

- 名称
- 标签
- enabled
- provider
- base_url
- api_key
- model
- timeout
- temperature
- max_tokens
- thinking
- reasoning_effort
- response_format
- system_prompt

状态：

- 查看态
- 编辑态
- 新建态

操作：

- `测试模型`
- `保存`
- `设为 ACTIVE`
- `删除`

输出区保留：

- 测试输出
- 保存反馈

---

## 8. 子页面三：webhook配置

## 8.1 作用

`webhook配置` 作为全局可复用的推送端点配置中心，用于支撑以下业务对象把产出物推送到第三方：

- `飞连API任务`
- `飞连周期任务`
- `运营agent`

这里采用你确认的关系：

> **全局配置 + 业务引用**

也就是说：

- `webhook配置` 负责维护 webhook 端点
- 业务对象只引用某个 `webhook_config_id`

而不是每个任务/调度/运营agent 自己手填一套 webhook 地址。

---

## 8.2 左侧列表

每条记录建议展示：

- 名称
- webhook URL（可做截断）
- method
- 状态（enabled / disabled）
- `ACTIVE` 或 `DEFAULT` 标记（如后续需要默认 webhook）

操作：

- `查看`
- `删除`

备注：

- 是否需要 `ACTIVE` 取决于后续是否支持默认 webhook
- 第一版可以先不强制 ACTIVE，只保留列表 + 查看 + 删除

---

## 8.3 右侧详情

字段建议包括：

- 名称
- webhook URL
- method
- headers
- auth 方式
- body template / payload template
- timeout
- retry count
- enabled

状态：

- 查看态
- 编辑态
- 新建态

操作：

- `测试推送`
- `保存`
- `删除`

---

## 8.4 测试推送能力

这是本次设计中必须要保留的能力。

右侧需要提供：

### A. 测试推送按钮

- 发送一条模拟 webhook 请求

### B. 模拟 payload 输入区

用户可以手工输入一个模拟 JSON，例如：

```json
{
  "title": "测试推送",
  "source": "连接配置",
  "content": "这是一条 webhook 测试消息"
}
```

然后点击 `测试推送`，输出结果写入配置输出区。

输出区需要展示：

- HTTP 状态
- 响应 body
- 错误信息

---

## 9. 业务对象与 webhook 的引用关系

未来以下对象需要支持引用 webhook 配置：

## 9.1 飞连API任务

建议新增字段：

- `webhook_config_id`
- `webhook_enabled`

## 9.2 飞连周期任务

建议新增字段：

- `webhook_config_id`
- `webhook_enabled`

## 9.3 运营agent

建议新增字段：

- `webhook_config_id`
- `webhook_enabled`

说明：

第一版不强制加入更复杂的控制项，例如：

- success 才推送
- failure 才推送
- 自定义事件类型

这些可以留到后续增强。

---

## 10. 页面交互路径

## 10.1 新增飞连API配置

1. 进入 `连接配置`
2. 切到 `飞连API配置`
3. 点击 `新增`
4. 在右侧输入详情
5. 点击 `测试连接`
6. 点击 `保存并热更新`

## 10.2 新增 LLM_API 配置

1. 进入 `连接配置`
2. 切到 `LLM_API配置`
3. 点击 `新增`
4. 填写单条模型 API 配置
5. 选择或录入标签
6. 点击 `测试模型`
7. 点击 `保存`

## 10.3 新增 webhook 配置

1. 进入 `连接配置`
2. 切到 `webhook配置`
3. 点击 `新增`
4. 填写 URL / method / headers / body template
5. 填写模拟 payload
6. 点击 `测试推送`
7. 点击 `保存`

## 11. 技术实现建议

## 11.1 前端

建议当前 `view-connection` 进一步拆成：

- 父级壳层
- 子页面切换器
- 每个子页面内部复用统一的左右布局组件

推荐复用的抽象：

- `config-list-panel`
- `config-detail-workbench`
- `config-output-panel`

## 11.2 后端

为了支撑这次改版，后端至少需要具备三类存储：

- 飞连 API 连接历史存储
- LLM_API 单条配置存储
- webhook 配置存储

并分别提供：

- 列表
- 查看
- 保存
- 删除
- 设为 ACTIVE（至少飞连_API 与 LLM_API 需要）

`webhook配置` 还需要：

- 测试推送接口

## 12. 风险与注意事项

## 12.1 `LLM_API配置` 模型已发生变化

这意味着前一版“LLM 配置集（planner + formatter 一组）”的设计思路需要被新设计取代。

新设计明确采用：

- 单条配置
- 标签表达用途

这会影响：

- 存储模型
- ACTIVE 语义
- 前端右侧表单结构

## 12.2 webhook 不是单纯的配置展示

如果只做静态配置，而没有：

- 测试推送
- 模拟 payload

那这个页面的可用性会很差。

因此本次设计明确建议：

- `webhook配置` 必须带测试能力

## 12.3 业务引用建议延后到实施计划中分阶段

因为：

- 配置中心搭建
- 引用能力改造
- 运行时真正执行推送

这是三个层次的问题。

推荐实施顺序：

1. 先把三子页面配置中心搭好
2. 再给业务对象加 webhook 引用字段
3. 最后接上真实推送执行链路

---

1. `连接配置` 下存在三个独立子页面：
   - `飞连API配置`
   - `LLM_API配置`
   - `webhook配置`
2. 三个子页面都采用：
   - 左侧配置列表
   - 右侧配置详情
3. `LLM_API配置` 不再固定区分 `Planner 模型 / Formatter 模型`
4. `LLM_API配置` 支持标签：
   - 内置标签
   - 自定义标签
5. 新增 `webhook配置`
6. `webhook配置` 支持：
   - 测试推送
   - 模拟 payload 输入
7. 业务对象未来可通过 `webhook_config_id` 引用 webhook 配置
